sharedwatch

A calm collaboration bus for a local shared folder. Capture every change. Read on your own cadence.

MIT Go 1.22+ single binary SQLite-backed no daemon-spawning sub-processes no network until you ask

sharedwatch watches a folder on disk and writes every change (create, modify, delete, rename) into a durable SQLite queue. You — or an AI agent — read back digests on your own schedule. The watcher never interrupts the reader; the reader never blocks the watcher. They communicate through one append-only journal.

Install

curl -fsSL https://raw.githubusercontent.com/ab0t/sharedwatch/main/scripts/install.sh | bash

The installer checks SHA-256 against the release manifest before writing. Local-dev mode is auto-detected when run inside a checkout (uses scripts/rebuild.sh instead of downloading).

Or grab a tagged release tarball from the releases page.

What it is (and isn't)

It is

  • A single static Go binary that runs on one host.
  • A polling filesystem watcher (deliberate; portable, predictable, no kernel-specific wiring).
  • A durable SQLite journal of every observed change, with optional content hashing.
  • A pull-based digest API for humans (digest list / digest show) and for agents (events list with cursors, sql escape hatch).
  • Multi-root: one daemon, many labelled folders, per-root coalesce + rename detection.
  • Multi-actor: payload_json v1 with actor / session / task / intent / addressee / ref_event_id / tags; cooperative intents + advisory leases.

It is not

  • Not a git replacement — it records that a file changed, not byte-level history. (See design-questions Q1.)
  • Not a multi-host file share or sync service.
  • Not push-based — readers pull on their own cadence (passive 10 min, active 5 s).
  • Not a high-throughput pipeline — low-to-moderate write volume is the design centre.
  • Not a daemon that talks to the network — until you opt into update, every operation stays on this machine.

60-second quickstart

$ sharedwatch init watch_path=/home/you/.local/share/sharedwatch/watch db_path=/home/you/.local/share/sharedwatch/queue.db data_dir=/home/you/.local/share/sharedwatch $ sharedwatch run & # watcher + consumer + reconcile loop now running in the background $ echo "hello" > ~/.local/share/sharedwatch/watch/hello.md $ sharedwatch digest list dgs_1779580871393427045 2026-05-24T00:01:11Z events=1 status=pending Shared drive digest at 2026-05-24T00:01:11Z $ sharedwatch digest show dgs_1779580871393427045 # prints the full digest and marks it read

Usage examples by situation

Each accordion below covers one real situation. Click to expand. Outputs shown are real terminal captures, lightly trimmed for width.

1. Watch a single folder; read digests on your own cadence (the canonical flow)

Situation: you have one folder you want a calm ambient awareness of. You'll check in every 10–15 minutes.

$ sharedwatch --watch-path ./shared --db ./shared.db init watch_path=./shared db_path=./shared.db data_dir=./shared/.sharedwatch $ sharedwatch --watch-path ./shared --db ./shared.db run & # watcher polls every coalesce window; consumer runs every 10 min (passive) # or every 5 s (active). Reconcile pass every 30 min as the safety net. $ # ... time passes ... $ sharedwatch --db ./shared.db status mode=passive pending=12 failed=0 digests=3 unread_digests=2 archived_digests=0 \ active_until=- active_expires_in=- last_event=2026-05-24T00:01:02Z \ last_consumer=2026-05-23T23:50:00Z last_reconcile=2026-05-23T23:30:00Z $ sharedwatch --db ./shared.db digest list dgs_177958... 2026-05-24T00:01:11Z events=12 status=pending Shared drive digest dgs_177957... 2026-05-23T23:50:00Z events=8 status=read Shared drive digest dgs_177956... 2026-05-23T23:40:00Z events=3 status=read Shared drive digest
2. Multi-root: one daemon, many labelled folders

Situation: you're tracking three projects in three different folders, want a single queue, but need per-root scoping.

$ sharedwatch \ --root auth=/workspace/projects/auth \ --root billing=/workspace/projects/billing \ --root frontend=/workspace/projects/frontend \ --db ./shared.db run & $ # Per-root status, as JSON: $ sharedwatch --db ./shared.db status --json | jq '.roots' [ { "label": "auth", "path": "/workspace/projects/auth", "pending": 3, "last_event_at": "2026-05-24T00:01:02Z", "ok": true }, { "label": "billing", "path": "/workspace/projects/billing", "pending": 9, "last_event_at": "2026-05-23T23:59:14Z", "ok": true }, { "label": "frontend", "path": "/workspace/projects/frontend", "pending": 0, "last_event_at": null, "ok": true } ] $ # Filter events for one root only (note: --root used as filter here, not definition): $ sharedwatch --db ./shared.db events list --root auth --since 1h --format jsonl {"id":"evt_...", "type":"file.modified", "rel_path":"login.go", "watch_root":"auth", ...} {"id":"evt_...", "type":"file.created", "rel_path":"login_test.go","watch_root":"auth", ...}
Invariants: coalesce and rename detection are root-scoped. Two README.md files in different roots never merge. Filter-mode --root <label> uses bare label (no =path); definition-mode requires --root <label>=<path>.
3. Attribute every event to an actor (humans, AI agents, automation)

Situation: multiple writers share the same folder. You want to know who did what.

The payload_json v1 schema carries actor / session / task / intent / addressee / ref_event_id / tags. Attribution flags can be set on the root flagset (apply to every event the invocation emits) or on test emit (per-event).

$ # Stamp every event from this daemon lifetime: $ sharedwatch \ --actor claude-coordinator-1 --actor-kind ai_agent \ --session sess-2026-05-24-abc \ --task refactor-auth \ --intent "split monolithic login.go into login/, signup/, logout/" \ run $ # Emit one attributed synthetic event: $ sharedwatch test emit specs/widget.md \ --actor claude-spec --actor-kind ai_agent \ --task new-widget-spec \ --addressee claude-code \ --tag spec --tag widget emitted evt_79b64ece7905adcd specs/widget.md $ sharedwatch events list --limit 1 --format jsonl { "id": "evt_79b64ece7905adcd", "type": "file.modified", "rel_path": "specs/widget.md", "created_at": "2026-05-24T00:01:02.712Z", "producer_id": "ip-172-31-22-90:92088", "payload_json": "{\"schema_version\":1,\"actor\":\"claude-spec\",\"actor_kind\":\"ai_agent\", \"task\":\"new-widget-spec\",\"addressee\":\"claude-code\", \"tags\":[\"spec\",\"widget\"]}" }
4. "What's new since I last looked?" — server-side cursors

Situation: your agent runs every few minutes and wants to consume only events it hasn't seen.

$ # First call. Cursor "my-agent" doesn't exist yet, so this returns # everything from oldest to newest (ASC over (created_at, id)) and # advances the cursor to the last returned row. $ sharedwatch events list --cursor-name my-agent --limit 100 --format jsonl {"id":"evt_a","type":"file.created", ...} {"id":"evt_b","type":"file.modified",...} ... {"id":"evt_z","type":"file.modified",...} $ # Next call. Returns only events newer than where my-agent left off. $ sharedwatch events list --cursor-name my-agent --format jsonl {"id":"evt_aa","type":"file.modified",...} {"id":"evt_ab","type":"file.deleted", ...} $ # Peek without advancing: $ sharedwatch events list --cursor-name my-agent --no-advance --format jsonl $ # Reset if you want to re-process from the beginning: $ sharedwatch events cursor reset my-agent
5. Self-discovery: schema, status, multi-root

Situation: your agent doesn't know the schema yet. Run these once per session and cache.

$ sharedwatch schema --format json | jq 'keys' [ "actors", "cursors", "digests", "events", "intents", "leases", "runtime_state", "snapshots" ] $ sharedwatch status --json { "format_version": 1, "mode": "passive", "pending": 0, "failed": 0, "digests": 0, "unread_digests": 0, "archived_digests": 0, "last_event_at": "2026-05-24T00:01:02.717Z" }
6. Progressive disclosure: overview → stats → list

Situation: you want an L1 overview before drilling. Each endpoint returns a drill map of pre-computed follow-up commands.

$ sharedwatch overview --format json { "format_version": 1, "generated_at": "2026-05-24T00:01:18Z", "since": "24h0m0s", "mode": "passive", "pending": 0, "failed": 0, "events_in_range": 1, "by_type": [{"type":"file.modified", "count":1}], "top_actors": [{"actor":"demo-agent", "count":1}], "drill": { "actor:demo-agent": "sharedwatch events list --payload-key actor --payload-value demo-agent --since 1h --format jsonl", "events_by_type": "sharedwatch sql \"SELECT type, COUNT(*) FROM events GROUP BY type\"", "events_failed": "sharedwatch events list --status failed --format jsonl", "events_recent": "sharedwatch events list --since 1h --format jsonl" } }

Then narrow with events stats --root <label> (L2, per-root), and finally events list (L4) for the raw rows.

7. SQL escape hatch (read-only by default)

Situation: the projected columns aren't quite right; you want raw SQL.

$ sharedwatch sql "SELECT type, COUNT(*) AS n FROM events GROUP BY type ORDER BY n DESC" --format json [ {"type":"file.modified","n":42}, {"type":"file.created", "n":11}, {"type":"file.deleted", "n": 3} ] $ # Anything not SELECT/WITH/EXPLAIN/PRAGMA table_info is refused unless --write: $ sharedwatch sql "UPDATE events SET status='processed' WHERE id='evt_x'" error: refusing to run a write statement without --write (tripwire, not a security boundary)
This is a tripwire, not a security boundary. The DB file is right there on disk; --write exists for cases where you genuinely need to mutate.
8. Multi-agent handoff (cooperative coordination)

Situation: agent A writes a spec; agent B reads the spec and writes code; agent A wants to know it's been picked up.

$ # A registers + heartbeats so B can see them in `status --actors`: $ sharedwatch actor heartbeat claude-spec --kind ai_agent --focus 'specs/**' $ # A declares an intent (cooperative — peers SHOULD respect it): $ sharedwatch intent declare 'specs/widget.md' \ --actor claude-spec --ttl 5m --intent "drafting widget spec" $ # A writes the spec. The change auto-attributes to claude-spec # because the root attribution flags were set: $ echo "..." > specs/widget.md $ # B looks for things addressed to them: $ sharedwatch events list \ --payload-key addressee --payload-value claude-code \ --format jsonl $ # B emits a response, ref'ing A's event id (causal chain): $ sharedwatch test emit src/widget.go \ --actor claude-code --task implement-widget \ --ref evt_79b64ece7905adcd --addressee claude-spec
9. Operational hygiene: retry, recover-stuck, reconcile

Situation: something went wrong during consume; events are stuck.

$ # Re-queue events that failed: $ sharedwatch events retry --max-retries 3 $ # Recover events stuck in 'processing' state for >5 min # (typically from a crashed consumer): $ sharedwatch events recover-stuck --older-than 5m $ # Force an immediate reconcile pass — re-diffs the folder against # the last snapshot and enqueues recovery events for anything missed: $ sharedwatch reconcile now

Keeping the binary current

The update command is safe by default. Running it bare prints what would change and exits. Pass --apply to actually install.

$ sharedwatch update current version: v0.0.2 target version: v0.0.3 repo: ab0t/sharedwatch platform: linux_amd64 binary path: /home/you/.local/bin/sharedwatch download: https://github.com/ab0t/sharedwatch/releases/download/v0.0.3/sharedwatch_0.0.3_linux_amd64.tar.gz manifest: https://github.com/ab0t/sharedwatch/releases/download/v0.0.3/manifest.yaml DRY RUN — no changes made. To apply: sharedwatch update --apply $ sharedwatch update --apply current version: v0.0.2 target version: v0.0.3 ... Replace /home/you/.local/bin/sharedwatch with v0.0.3 ? [y/N] y downloading manifest... downloading tarball (~few MB)... verifying SHA-256... expected: 5e2c...d0b actual: 5e2c...d0b OK extracting binary... smoke-testing new binary... installed v0.0.3 to /home/you/.local/bin/sharedwatch if a daemon is running, restart it to pick up the new binary

What "safe" means here

  • Dry-run by default. Bare sharedwatch update reads metadata and prints a plan. No download, no write.
  • SHA-256 verification. The tarball's hash must match the entry in the release's manifest.yaml before extraction. Mismatch aborts cleanly.
  • Smoke test before swap. The downloaded binary must execute and report a sharedwatch version banner before it's installed. A broken binary never replaces a working one.
  • Atomic install. rename(2) on the binary path. Either you have the old binary or the new one — never a half-written file.
  • No sudo escalation. Refuses if the binary's parent directory isn't writable by the current user.
  • Safe to run while the daemon is active. On POSIX, the running process holds the old inode. The new binary takes effect on next restart.
  • Touches nothing but the binary. No DB write, no config change, no watched-folder write.
  • Bounded network time. --timeout 60s by default.
  • Pin a specific version. --version v0.0.2 overrides "latest". Useful for rollback.

How it works (architecture sketch)

filesystem ──▶ watcher (polling diff, per-root)
                  └▶ coalesce (rel_path + actor + watch_root)
                        └▶ SQLite events table (pending)
                              │
                              ▼ pull
                        consumer (passive 10m | active 5s)
                              └▶ digests table
                                    │
                                    ▼ pull
                              you / your agent

separately, every reconcile_interval (default 30m):
   snapshot ──▶ diff vs last reconcile snapshot ──▶ recovery events

Three independent moving parts, all writing through one SQLite DB with WAL mode + foreign-key cascade. Single-process, single-host. The polling-not-fsnotify choice is a deliberate v1 simplification — predictable across kernels, no platform-specific wiring.
