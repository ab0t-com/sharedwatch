## 1. Business rationale

### 1.1 What problem does this solve?

The sharedwatch journal is the integration surface today. Any consumer that wants to react to events does `events list --cursor-name <me>` on a poll loop and pipes the result somewhere — a pattern documented in the Skill and the agent-system-prompt. This works for **steady-state agent consumers** (who already poll on their own cadence) but is awkward for **event-driven integrations** where the consumer is:

- A notification system (Slack, email, PagerDuty) that should fire when *meaningful* activity lands — not on every file change.
- A pipeline trigger that should kick off a downstream build/deploy/ingest when human-significant activity accumulates.
- An archive/audit fan-out that wants every digest copied to S3 / GCS / a long-term log.
- A user's shell environment (the human operator) that wants a desktop notification when their watched folder has been busy enough to produce a digest.

For these consumers, today's only option is to write a poll-loop script that periodically calls `digest list --json` and diffs against the last seen id. That's:
- 30+ lines of error-prone shell per integration
- Polling latency (the poll interval == reaction delay)
- Duplicate state machinery per integration (each script tracks "what's the last id I processed")

The hook surface collapses all of that to a single flag.

### 1.2 Why ship it now (vs. the original "defer" verdict)

The original discussion doc (2026-05-24, earlier this session) recommended **don't build speculatively**. Three things justify revisiting:

1. **User explicitly asked.** That's the gating condition the doc said to watch for.
2. **Scope is honestly small** (~150 LOC + 2 flags + 1 call site + a handful of tests). The cost of building is now lower than the cost of not having it for the kinds of integrations described above.
3. **Calm-contract risk is low** by design. The hook fires only when the **consumer voluntarily produces a digest** — never on every event. The push-shape that would break the calm contract was per-event hooks, which we are explicitly NOT building.

### 1.3 What it is NOT solving (explicitly out of scope)

- **Per-event reactions.** If you need that, write a cursor-tail script. Push-shape hooks at the event layer would re-introduce the latency-sensitive coupling we got rid of by making the watcher pull-based.
- **Native webhook POST.** `--on-digest "curl -X POST https://..."` is strictly more flexible than a built-in webhook (custom headers, retries via shell, TLS pinning all become the operator's choice). We won't ship a `--webhook` flag.
- **Plugin systems / Go-plugin loading.** Massive overkill for a single-host daemon.
- **Synchronous "veto" hooks.** The consumer never waits on a hook. A hook that times out / fails does not block the digest from being committed.

## 2. User value — who uses this, when, where, how?

### 2.1 Persona A — Solo developer, desktop notifications

> "I want my OS to ping me when my project folder has had enough activity to be worth glancing at, but not on every save."

```bash
sharedwatch run --on-digest 'notify-send sharedwatch "$(jq -r .summary)"'
```

The hook receives the digest JSON on stdin; `notify-send` triggers a desktop toast. They get one notification per consume cycle — not one per file save.

### 2.2 Persona B — Team using a shared design folder, Slack notifications

> "When the design folder is busy, let the channel know — but only when activity has rolled up into something coherent."

```bash
sharedwatch run --on-digest '
  jq -r .summary |
  xargs -I{} curl -s -X POST -H "Content-Type: application/json" \
    -d "{\"text\":\"sharedwatch digest: {}\"}" \
    "$SLACK_WEBHOOK_URL"'
```

Each consume → one Slack post with the digest summary. Slack rate-limiting is the operator's problem (they can wrap the curl in a debounce, batch, or queue — the flag stays simple).

### 2.3 Persona C — AI agent coordinating with peer agents

> "When a digest is created, I want my peer-discovery agent to also know about it, so it can route work to whoever is idle."

```bash
sharedwatch run --on-digest 'curl -X POST http://localhost:8081/sharedwatch-digest -d @-'
```

The peer-discovery agent (running on the same host) gets a real-time push instead of having to poll `digest list --json`. Latency drops from "next poll interval" to "next async tick".

### 2.4 Persona D — Operations / compliance, audit fan-out

> "Every digest needs to land in our long-term audit store so we can prove activity over time."

```bash
sharedwatch run --on-digest 'aws s3 cp - "s3://audit-bucket/sharedwatch/$(date -u +%Y/%m/%d)/$(jq -r .id).json"'
```

Every digest becomes an S3 object. Zero sharedwatch code per integration; the operator owns the S3 path scheme, retention, encryption.

### 2.5 Persona E — Pipeline trigger, downstream build

> "When my data ingestion folder gets a digest, kick the ingest job."

```bash
sharedwatch run --on-digest 'make ingest DIGEST_ID=$(jq -r .id)'
```

Digest → make target. Build system handles its own queueing / debouncing.

### 2.6 When does the hook fire?

- After **every** successful digest INSERT.
- Fires from both `consume` (one-shot) and `run` (daemon loop).
- Fires **once per digest** (Q1 default per the design doc). If a consume run produces N digests, the hook fires N times.
- Fires **after** the digest row commits to SQLite — the script will never see a half-built digest, and `digest show <id>` from inside the hook will succeed.

### 2.7 Where does the hook execute?

- Same host as the daemon.
- Same user as the daemon (no privilege escalation).
- Via `sh -c "<command>"` (full shell semantics — pipes, env vars, glob, etc.).
- Stdin: digest JSON object.
- Stdout + stderr: captured to `<data_dir>/hooks/<digest_id>.{out,err}` sidecar files (Q2 default).
- Working directory: daemon's CWD (whatever `sharedwatch run` was launched from).
- Environment: inherited from the daemon process.

## 3. Event / hook surface to be exposed

### 3.1 New CLI flags

| Flag | Scope | Default | Description |
|---|---|---|---|
| `--on-digest <shell-command>` | `run`, `consume` | unset | Fire this command (via `sh -c`) after each digest is committed. Digest JSON sent to stdin. Empty string disables. |
| `--on-digest-timeout <duration>` | `run`, `consume` | `30s` | Hard timeout for the hook subprocess. On timeout, child is killed and a `hook.failed` meta-event is written with `reason: timeout`. |

Both flags are addable to `config.yaml` as `on_digest:` and `on_digest_timeout:` for daemon configs. Resolution: flag > env (`SHAREDWATCH_ON_DIGEST`, `SHAREDWATCH_ON_DIGEST_TIMEOUT`) > config > default.

### 3.2 Hook stdin contract

```json
{
  "format_version": 1,
  "id": "dig_a1b2c3d4e5f6g7h8",
  "created_at": "2026-05-24T09:17:30Z",
  "watch_root": "code",
  "status": "unread",
  "summary": "10 file events: 6 modifications under src/auth/, 3 creations under tests/, 1 deletion",
  "event_count": 10,
  "first_event_id": "evt_xxxx",
  "last_event_id": "evt_yyyy"
}
```

The keys mirror what `digest show --json` already emits (so consumers can use the same `jq` recipes either way). `format_version: 1` is the envelope version for forward-compat.

### 3.3 Meta-events written to the journal

After every hook run, one meta-event lands in the events journal:

```json
{
  "type": "hook.completed",          // or "hook.failed"
  "rel_path": "<digest_id>",
  "source": "hook",
  "status": "processed",
  "payload_json": "{
    \"hook_command\": \"notify-send ...\",
    \"digest_id\": \"dig_a1b2c3d4e5f6g7h8\",
    \"exit_code\": 0,
    \"duration_ms\": 124,
    \"stdout_bytes\": 0,
    \"stderr_bytes\": 0,
    \"stdout_path\": \"<data_dir>/hooks/dig_a1b2.../out\",
    \"stderr_path\": \"<data_dir>/hooks/dig_a1b2.../err\",
    \"reason\": null
  }"
}
```

On failure, `reason` is one of `timeout`, `nonzero_exit`, `spawn_error`. Inline stdout/stderr is NOT carried in the payload (Q5 default) — only sizes + sidecar paths. This keeps the journal lean while still being inspectable from agents that have shell access.

### 3.4 Sidecar files

```
<data_dir>/hooks/
├── dig_a1b2c3d4e5f6g7h8.out    # full stdout
├── dig_a1b2c3d4e5f6g7h8.err    # full stderr
├── dig_x1y2z3...out
└── dig_x1y2z3...err
```

These get pruned by the existing `retention_days` pass alongside processed events (Q2 default). No new retention knob — keeps the config surface small.

### 3.5 What the hook surface DOES NOT expose

- No per-event hook flag (`--on-event`). Build only when a real use case demonstrates the `--on-digest` shape is insufficient.
- No hook for lease violations, intent declares, actor heartbeats, etc. The journal carries those events; consumers wanting to react to them write a cursor tail.
- No structured "hook configuration file" with N hooks. One flag, one command. If you want a chain, your command is a wrapper script.
- No retry logic. Failed hooks are visible via meta-events; retry policy is the caller's problem.
- No webhook-specific code path. The `curl` recipe is the supported way to POST.

## 6. Acceptance criteria

- [ ] `sharedwatch run --on-digest 'echo $(jq .id)' --on-digest-timeout 5s` works against a real consume and prints the digest id to the daemon's stdout.
- [ ] `sharedwatch consume --on-digest 'cat > /tmp/last-digest.json'` writes the digest JSON to `/tmp/last-digest.json`.
- [ ] `events list --type hook.completed --type hook.failed` surfaces every hook run with the correct payload shape (§3.3).
- [ ] A failing hook (`--on-digest 'false'`) emits `hook.failed` with `exit_code: 1` and `reason: nonzero_exit`.
- [ ] A hanging hook (`--on-digest 'sleep 999'` with `--on-digest-timeout 1s`) is killed; `hook.failed` lands with `reason: timeout`.
- [ ] Stdout from the hook is captured to `<data_dir>/hooks/<digest_id>.out`; stderr to `.err`.
- [ ] Graceful shutdown (`sharedwatch stop`) waits for in-flight hooks (bounded) before exiting.
- [ ] `go test ./...` passes; no new lint warnings.

## 7. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Slow hook backpressures the consumer | Async fire-and-forget; consumer returns immediately. WaitGroup at daemon level prevents goroutine leak on shutdown only — runtime never waits. |
| Hook fork-bombs on a busy folder | The hook fires per **digest**, not per event. Even a frantic folder produces at most ~12 digests/hour in passive mode, ~720/hour in active mode. That's well within sustainable subprocess rates. |
| Hook writes massive output | Captured to sidecar files (bounded by disk, not memory). Retention pass cleans them. |
| Hook misconfigured (binary missing) | First fire emits `hook.failed` with `reason: spawn_error`. Visible on next `events list`. |
| Daemon crashes mid-hook | Subprocess is orphaned (POSIX behaviour). On next daemon start, a routine startup check could log INFO if any expected `hook.completed`/`hook.failed` is missing — defer this enhancement; not P0. |
| Hook is used to attack the daemon (privilege escalation via shell injection) | The hook command is operator-supplied at daemon start. Same trust boundary as setting `$PATH` or `/etc/cron.d/*`. Document explicitly that the command runs with the daemon's privileges. |

## 9. Out-of-scope follow-ups (do NOT do in this ticket)

- `events subscribe` long-running subcommand. The design doc considered it (Alt 1) — defer until the cursor-tail script pattern shows real UX pain.
- `--on-event <cmd>` per-event hook. Strictly off the table without further design discussion.
- Webhook POST as a first-class flag. Use `curl` in the `--on-digest` command.
- Plugin loading. Off the table.
- Hook chain config (N hooks declared in a YAML file). Wrapper script is the supported answer.
