### Restated understanding (before code lands)

Phase 1 is **pure config plumbing — zero behaviour change to event emission yet.** No `ShouldEmit` function, no new event types, no emit sites. Only the data path through which Phase 2+ will read what to do.

Five things land in this phase:

1. **`config.Config` struct** gets three new fields:
   - `EmitProfile string` (default `"standard"`)
   - `EmitOverrides map[string]bool` (default empty map, so `cfg.EmitOverrides["foo"]` is a safe zero-value read)
   - `EmitThresholds map[string]int` (default `{events_failed:50, events_stuck:10, reconcile_drift:25}`)

2. **YAML loader** (`internal/config/file.go`) gets three new keys parsing inline-map syntax:
   - `emit_profile: standard`
   - `emit_overrides: actor_heartbeats=true,reconcile_per_cycle=false`
   - `emit_thresholds: events_failed=50,events_stuck=10,reconcile_drift=25`
   The inline-map shape mirrors the existing `watch_roots:` parser; we hand-roll a `k=v,k=v` splitter for bool and int values.

3. **Env vars** (`cmd/sharedwatch/env_glue.go`):
   - `SHAREDWATCH_EMIT_PROFILE`
   - `SHAREDWATCH_EMIT_OVERRIDE` (note: singular by convention — same pattern as `SHAREDWATCH_FORMAT`)
   - Both added to `knownEnvVars` so `config show` lists them.
   - Thresholds are intentionally **NOT** exposed via env vars — operator-only knob (avoid over-engineering).

4. **Root flags** (`cmd/sharedwatch/main.go`):
   - `--emit-profile <tier>`
   - `--emit-override <k=v>` (repeatable; uses the existing `csvList` shape adapted for k=v)
   - Resolution chain: flag > env > config > default. Same pattern `OnDigest` already uses.

5. **`config show` extensions** (`cmd/sharedwatch/config_show.go`):
   - DTO gets `emit_profile`, `emit_overrides`, `emit_thresholds` keys (snake_case, no omitempty so empty renders as `{}`/`""` — H8-B lesson from SW-AGENT-29).
   - Text-mode rows in the table.
   - **Derived `emit_effective_classes` map** showing which classes will actually emit after profile + overrides resolve. This is the operator-verification surface — "did my config land right?"

### Robustness commitments (this is what "project expects robust engineering" means here)

- **Validation at config-resolution time, not at emit time.** Invalid `emit_profile` value → log a warning + fall back to `standard`. Never silently mis-emit; never fatal (config files mustn't brick the daemon).
- **Unknown class names in overrides are silently ignored** (forward-compat — Phase 2's class table may grow). Documented in the loader comment.
- **Override value must parse as a clean bool.** `=true` / `=false` / `=1` / `=0` / `=yes` / `=no` accepted; anything else → warn + skip. Don't accept ambiguous truthy strings.
- **Threshold values must be non-negative integers.** Negative → warn + skip the entry. Zero = disable threshold-gating (semantically meaningful; documented).
- **Map fields are always non-nil** post-`Default()`. Avoid the nil-map-write panic.
- **Empty env var = "not set"** (existing convention).
- **No global state.** Resolution lives entirely in `cfg` and the flag layer.
- **Backwards compat**: a v0.0.x `config.yaml` with no `emit_*` keys gets `EmitProfile=standard` + empty overrides + default thresholds. Equivalent to default v0.1.0 behaviour. Existing tests should still pass without modification.

## 0. What this ticket delivers

Per the principle reframe: **emit liberally, hooks stay narrow.** This ticket fills out the event surface (~20 new event types) and adds the tier-profile config that lets clients choose what they consume.

Existing features are **unchanged and extended**, not replaced:
- File events still emit unconditionally at all tiers (including `minimal`).
- `--on-digest` hook surface from SW-AGENT-29 is untouched. New event types compose with it.
- All cursor / filter / format semantics remain unchanged. New types use the existing surface for free.
- Retention pipeline unchanged. New types prune at `retention_days`.

What's NEW:
- ~20 new event types covering daemon lifecycle, mode transitions, reconcile observability, retention evidence, failure thresholds, coord events (lease/intent), actor lifecycle, and optionally actor heartbeats / mode TTL extensions.
- 5 new event sources: `daemon`, `mode`, `coord`, `actor`, `retention`. (Existing `watcher`, `reconciler`, `test`, `hook` untouched.)
- A `internal/events/profile.go` package with a `ShouldEmit(eventType, profile, overrides) bool` central authority. Every emit site routes through it.
- Tier-profile config (`emit_profile` + `emit_overrides` + `emit_thresholds`) with smart defaults — see §2.
- Documentation: a new `docs/guides/event-broker.md` operator-facing guide written from the consumer catalog in the discussion doc.

## 1. Decisions baked into this tasklist

Per `docs/design/event-broker-consumer-contracts-20260525.md` §6, resolved best-practice with no over-engineering:

| OQ | Decision | Reasoning |
|---|---|---|
| OQ-1: explicit `digest.created` event? | **YES** | Symmetry — every other operation emits an event. Cost: one `InsertEvent` call. |
| OQ-2: separate `emit_thresholds` map? | **YES, with only 3 thresholds** | Keeps toggles separate from tuning. Three thresholds (`events_failed`, `events_stuck`, `reconcile_drift`); don't generalise to "configurable for everything." |
| OQ-3: per-class vs per-event override granularity? | **per-class for v1** | Classes are small enough; revisit only if users actually ask for per-type. |
| OQ-4: per-root emit profiles? | **uniform for v1** | Per-root multiplies config complexity for zero demonstrated demand. |

Additional decisions:

| Q | Decision | Reasoning |
|---|---|---|
| Default tier | `standard` | Covers ~95% of integration cases per the consumer catalog. |
| Rising-edge for threshold events | **YES** | `events.failed_threshold` fires when count crosses N upward; not every reconcile cycle while count stays above. Mitigates paging spam. |
| New sources or reuse existing? | **New per-class** | `daemon`, `mode`, `coord`, `actor`, `retention` — each its own source. Enables `--source daemon` queries. |
| Watch-root propagation | **Daemon-wide events: empty `watch_root`. Per-root events: stamped.** | Convention; documented in broker guide. |
| Backwards compat for new types at `minimal` tier | **All NEW types are above `minimal`** | A user on `minimal` gets exactly v0.0.x event surface — no surprise emissions. |

## 2. Configuration shape (final)

```yaml
emit_profile: standard            # default; minimal | standard | verbose | all
emit_overrides:                   # optional
  actor_heartbeats: true          # opt INTO a verbose-tier class
  reconcile_per_cycle: false      # opt OUT of a standard-tier class
emit_thresholds:                  # optional, only 3 knobs
  events_failed: 50               # rising-edge: fire when failed count crosses 50
  events_stuck: 10                # rising-edge: fire when stuck count crosses 10
  reconcile_drift: 25             # fire when recovered count > 25 in one pass
```

Env vars (resolution chain: flag > env > config > default):
- `SHAREDWATCH_EMIT_PROFILE=standard`
- `SHAREDWATCH_EMIT_OVERRIDE=actor_heartbeats=true,reconcile_per_cycle=false` (comma-separated key=bool list)

Root flags:
- `--emit-profile <tier>`
- `--emit-override <class>=<bool>` (repeatable)
- (Thresholds are operator-only config-file knobs; no flag.)

`config show` extensions:
- text mode: rows for `emit_profile`, `emit_overrides`, `emit_thresholds`
- JSON mode: same keys in the `effective` envelope, plus a **derived** `emit_effective_classes` showing which classes actually emit after profile + overrides resolve

### Phase 4 — emit sites (the bulk of the work)

Each emit site wraps in `if profile.ShouldEmit(t, cfg.EmitProfile, cfg.EmitOverrides) { _ = store.InsertEvent(ctx, ...) }`. Failures are non-fatal (log + continue) so emit issues never block real work.

- [ ] **4.1** `digest.created` — `consumer.ConsumePending` after `InsertDigest` succeeds. Threaded via the existing app.App `FireHookAsync` pattern OR a new `EmitDigestEvent` helper.
- [ ] **4.2** Daemon lifecycle — `app.App.Run` and `cmd/sharedwatch/main.go` shutdown path:
  - `daemon.started`: after lock acquired, before main loop.
  - `daemon.stopping`: in the deferred close path (before `WaitForHooks`).
  - `daemon.crashed`: in `acquireRunLock` when stale-lock detection fires.
- [ ] **4.3** Mode transitions — `app.App.SetActive` / `SetPassive`. Detect transition by comparing prior runtime state vs. new state. Emit `mode.changed` on actual transitions; emit `mode.ttl_extended` (verbose) on every TTL extension.
- [ ] **4.4** Reconcile observability — `reconcile.postPasses`:
  - `reconcile.ran` (verbose): always, with stats.
  - `reconcile.drift_detected` (standard): when `events_recovered > threshold`.
  - `reconcile.recovered_threshold` (standard): when count crosses `emit_thresholds.reconcile_drift` upward.
- [ ] **4.5** Retention pass — `reconcile.postPasses` after `PruneArchivedDigests` etc.: emit `retention.ran` with counts.
- [ ] **4.6** Failure thresholds — `reconcile.postPasses`:
  - `events.failed_threshold`: count `failed` rows; rising-edge against `emit_thresholds.events_failed` (track prior count in runtime state).

## 7. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Verbose-tier emission floods a test environment and breaks unrelated tests | Default tier in tests is `minimal` (or whatever the existing tests assume); verbose is opt-in per-test. |
| New event types collide with future user expectations | Type names follow the existing `<class>.<verb>` convention. Reserve `*` prefixes (no `*.timeout` namespace conflicts). |
| Rising-edge state for thresholds gets lost on daemon restart | Store the prior count in `runtime` row (same place `LastReconcileRun` lives). Restart sees the prior threshold-state; doesn't re-fire on resume. |
| Coord events fire from multiple call sites (CLI grant + reconcile expiry) and double-count | Each emit site is one specific lifecycle step; never both fire for the same `lease_id`. Acceptance tests verify. |
| Threshold defaults are too sensitive / too lax for real workloads | Defaults are tunable via `emit_thresholds` map. Document expected ranges in the broker guide. |
| `digest.created` event arrives BEFORE the `hook.completed` event for the same digest (consumers seeing them in unexpected order) | Document the ordering: `digest.created` ALWAYS lands first (sync from consumer); `hook.completed` follows async after the hook subprocess finishes. |
